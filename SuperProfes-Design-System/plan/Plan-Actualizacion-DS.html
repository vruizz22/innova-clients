Reconciliar el design system con el codebase innova-clients

El codebase ya avanzó por delante de la especificación: nuevas superficies, 12+ pantallas y una capa de tokens consumible que el design system aún no refleja. Este plan cierra esa brecha en 5 fases, sin tocar nada todavía.

9 pantallas nuevas 2 superficies nuevas 4 drifts de token 1 archivo fuera de escala
00

Punto de partida

El design system se escribió como especificación, antes de que existiera código real. El README lo deja anotado como open issue #1: "No real client codebase yet. Designs are spec-derived. Reconcile when innova-clients ships." Ese momento llegó. La carpeta local ya contiene la implementación, y al compararla con el DS del proyecto aparece una brecha concreta y acotada.

La buena noticia: los fundamentos coinciden. El colors_and_type.css es byte-idéntico entre ambos, así que la paleta, la tipografía Inter y la escala de espaciado no requieren migración. El trabajo está en incorporar lo nuevo y resolver pequeños desajustes en la capa de tokens consumible por código.

02

Drift de tokens

El tokens.ts del codebase no está alineado con la fuente de verdad (colors_and_type.css). Estos desajustes hay que resolverlos antes de importar pantallas, para no propagar valores divergentes.

TokenConflictoResolución
colors.canvasApunta a var(--bg-canvas), pero el CSS no define esa variable (tiene --bg y --bg-subtle). Referencia colgante.DECIDIR
radius.xlCodebase dice 18px; el CSS dice --r-xl: 16px. Valores en conflicto.ALINEAR
radius.2xlExiste en código (24px) pero falta como --r-2xl en el CSS.AÑADIR
radius.* / spacing.*Hardcodean píxeles ('12px', '24px') mientras que colors.* sí referencian var(--…). Inconsistencia estructural: dos fuentes de verdad.UNIFICAR
DESIGN_CSS_PATHRuta absoluta hardcodeada '/design-system/colors_and_type.css'. Frágil ante cambios de despliegue.REVISAR

04

Plan de actualización

Cinco fases en orden de dependencia: primero la base de tokens, luego el contenido, al final la documentación.

1

Reconciliar la capa de tokens

Base · debe ir primero
  • Decidir el valor canónico de --r-xl (16 vs 18) y alinear código y CSS.
  • Añadir --r-2xl: 24px al CSS, o eliminar radius.2xl de tokens.ts.
  • Definir --bg-canvas en el CSS o reapuntar colors.canvas a un token existente.
  • Hacer que radius y spacing referencien var(--…) igual que colors — una sola fuente de verdad.
Resultado: el CSS vuelve a ser la única fuente de verdad; SP_TOKENS solo lo expone a TypeScript.
2

Importar las pantallas nuevas

Mayor volumen de contenido
  • Copiar al proyecto las 7 pantallas de teacher/, las variantes web/mobile/onboarding/ocr-upload y la landing real.
  • Etiquetar cada una con @dsCard para que aparezcan en la pestaña Design System, agrupadas por superficie.
  • Verificar que cada pantalla carga tokens desde el CSS reconciliado (sin valores locales duplicados).
Resultado: el DS muestra el producto real, no una muestra parcial.
3

Documentar la superficie admin

Superficie nueva
  • Sumar admin como 5ª superficie en el README junto a student / parent / teacher / auth.
  • Definir su rol de paleta (probablemente la slate "grounded" del teacher) y patrones de estado del sistema.
  • Crear su tarjeta y README de UI kit replicando la estructura de las demás.
Resultado: ninguna superficie del producto queda sin especificar.
4

Pasada de adherencia

Calidad · transversal
  • Corregir admin/status.html: radios y bordes a la escala, colores ad-hoc a tokens semánticos (--warning-bg, --error-bg).
  • Pasar todas las pantallas importadas por las reglas de _adherence.oxlintrc.json.
  • Registrar como nuevos open issues cualquier desviación intencional que valga la pena conservar.
Resultado: el código nuevo cumple las mismas reglas que la spec.
5

Actualizar README y open issues

Cierre
  • Cerrar el open issue #1 ("No real client codebase yet") — ya está reconciliado.
  • Reescribir la sección de landing: de "Astro kit" abstracto a la implementación real.
  • Revisar los issues de Inter (Google Fonts → self-host) y de Lucide a la luz de lo que el codebase ya usa.
Resultado: la documentación describe el sistema que realmente existe.
05

Decisiones que necesito de ti

Antes de aplicar la Fase 1

  1. Radio XL: ¿el canónico es 16px (CSS actual) o 18px (codebase)? Define cuál se queda.
  2. --bg-canvas: ¿es un fondo nuevo que hay que añadir a la paleta, o colors.canvas debería apuntar a --bg-subtle?
  3. Superficie admin: ¿hereda la paleta slate del teacher, o quieres tratarla como una superficie con su propia identidad?
  4. Alcance: ¿importo las pantallas tal cual (rápido) o las normalizo a tokens al traerlas (más prolijo, más lento)?

Este documento es solo el plan — no se ha modificado nada del design system todavía. Dime por dónde empezamos y lo ejecuto fase por fase.
